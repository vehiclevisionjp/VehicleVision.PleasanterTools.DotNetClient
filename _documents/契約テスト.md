# 契約テスト（実機の Pleasanter）

Issue #68。生成したクライアントが、**実機の Pleasanter（公式の Docker イメージ）に通る**ことを確かめるテスト。
単体テストは `HttpMessageHandler` のフェイクだけなので、URL・本文・応答の形が実機と合っているかは、このテストで確かめる。

- **確かめたのは、最新版の 1 つだけ**（下の表）。1.3.0.0〜最新の版ごとの確認は別 Issue（#69）。1.3.x は、Docker Hub にある 1.3.29.0 以降だけが実機で試せる（1.3.29.0 は動いたが、現行の 14 件のうち 6 件が失敗し、原因は未切り分け。#69）
- Pleasanter 本体のコードは、複写・リンク・参照しない（公式イメージを起動して HTTP で呼ぶだけ）。ビルドにも NuGet パッケージにも含めない

## 実行のしかた

通常の `dotnet test` では、契約テストは**読み飛ばされる**（環境変数 `PLEASANTER_CONTRACT_TESTS=1` のときだけ動く。既定のビルド・CI を遅くしない）。

```bash
# Docker で Pleasanter を起こし、試験を流し、自分のコンテナだけを止める（初回はイメージの取得で数分）
bash tests/contract/run.sh
# 止めずに残す（画面を見たいとき）
bash tests/contract/run.sh --keep
# 既に動いている Pleasanter に当てる（Docker を扱わない）
CONTRACT_SKIP_DOCKER=1 PLEASANTER_BASE_URL=http://127.0.0.1:8080 PLEASANTER_API_KEY=<試験用のキー> bash tests/contract/run.sh
```

- `run.sh` は、DB のパスワードと API キーを**実行のたびに乱数で作り**、画面にもログにも出さない（リポジトリに秘密を置かない）。API キーは `Users.ApiKey` へ直接入れる（Pleasanter はそのまま比べる）
- compose のプロジェクト名は `dotnetclient-contract`（`CONTRACT_PROJECT` で変えられる）、ポートは `127.0.0.1:18095`（`CONTRACT_PLEASANTER_PORT`）。**後片付けはこのプロジェクトのものだけ**に行う。他のプロジェクトのコンテナには触れない
- 契約テストの接続の変数（`PLEASANTER_BASE_URL`・`PLEASANTER_API_KEY`）と、開発用の `PLEASANTER_CONTRACT_TESTS`・`PLEASANTER_EXPECTED_VERSION`・`PLEASANTER_REFERENCE_DIR` は、**共通の `VVPT_PLEASANTER_*` にしない**（`PleasanterOptions.FromEnvironment()` は読まず、`ContractEnvironment` が自前で読む）。実際の Pleasanter にデータを作る試験なので、開発者の端末に設定された本番接続の `VVPT_PLEASANTER_*` を、契約テストが拾わないようにする（Issue #116）
- 版は `CONTRACT_PLEASANTER_TAG`（既定 `1.5.9.1`）。`PLEASANTER_EXPECTED_VERSION` を渡すと、`GetLicenseInfo` の版が一致することも確かめる
- GitHub Actions の `contract.yml`（別ワークフロー。**必須チェックにしない**）が、PR（`src`・契約テスト関係の変更）・週 1 回・手動で同じスクリプトを流す

### 落とし穴（ClaudeMemory の `pleasanter-testenv-gotchas`・`pleasanter-warmup-503` と同じ）

- ポートが他と衝突すると Pleasanter が起動せず、`Administrator` も作られない → `run.sh` は先にポートを確かめる
- 起動・再起動の直後は、ポートが開いても API が 503 を返す（暖機）→ `/users/login` が 200 を返すまで待つ。再起動の後に `up --wait` をやり直さない
- CodeDefiner は失敗しても終了コード 0 を返す → ログの `SUCCESS` を確かめる
- 公式イメージの `Rds.json` は PostgreSQL を焼き込んでいるので、PostgreSQL では差し替えが要らない
- PostgreSQL 18 は、データのマウント位置が `/var/lib/postgresql`。表は、サービス名の名前のスキーマ（`"Implem.Pleasanter"."Users"`）にある
- Windows の Git Bash では、`MSYS_NO_PATHCONV=1` を付け、`docker`・`dotnet` に渡すパスは `cygpath -m` で直す（`run.sh` は済み）

## 確かめた範囲（1.5.9.1、2026-11-02）

14 のテストがすべて通った。

| 口 | 確かめたこと |
| --- | --- |
| `Utility.GetLicenseInfo`・`GetServerVersionAsync` | `Response.Version`（`1.5.9.1`）から版が取れる |
| `CheckConnectionAsync`・誤った API キー | 成功する。誤ったキーは 401・`Unauthorized` |
| サイト: `CreateSite`・`GetSite`・`UpdateSite`・`UpdateSiteSettings`・`DeleteSite` | URL・本文・応答の形。削除後の取得は失敗 |
| レコード: `Create`・`Get`（1 件・一覧）・`Update`・`Delete` | 同上。更新は送った項目だけを変える（`Body` が残る） |
| 一覧: ページ指定・並べ替え・絞り込み | `Api.Offset`・`PageSize`、`View.ColumnSorterHash` の列挙を**名前**（`"asc"`・`"desc"`）で送れる。`ColumnFilterHash`。応答の `Offset`・`PageSize`・`TotalCount` |
| `Upsert`・`BulkUpsert`・`BulkDelete`（`PhysicalDelete`・`RecordSelector.All`） | キー（`Keys`）での更新・作成、物理削除 |
| `Export` | 応答の `Name`・`Content` |
| ユーザー・グループ・組織: 作成・取得（ID 指定）・更新・削除 | URL・本文・応答の形 |
| `Sessions`（`Set`・`Get`・`Delete`） | 同上 |
| `Binaries.Upload`・`Get`・`GetStream` | ファイルの部品の名前 `file` で送れる。`Authorization: Bearer` で通る。応答の `Message` に GUID。取得したバイト列が一致 |
| 無い添付の `GetStream`・`Get` | 404・`Permanent`・`Content` は `null`（失敗として扱える） |
| クエリ文字列の真偽値（`BackgroundTasks.RebuildSearchIndexes?nolog=true`） | `true` で受け付けられる（200）。値が効いたかまでは確かめていない |
| `OutgoingMails.Send`（`{reference}` に `Results`） | 404 にならず、口には届く。送信の成否は、サーバーのメール設定・権限によるので、確かめていない（試験の環境では 403 だった） |
| `{controller}` の置き換え | `OutgoingMails` の URL が、実機で口に届いた（上の行） |

### 見つかった差・気づいたこと

- **`Items.CreateSiteAsync` は `SiteSettings` が必須**（`null` だと 400）。最上位のサイトは親の ID に `0` を渡す。`ItemsOperations.CreateAsync(0, SiteApiModel)`（`items/0/create`）は 404 になる。サイトを作るときは `CreateSiteAsync`（文書・README の例で触れる）
- `Items.GetAsync` の `Api.TableType`: `Deleted`・`Normal` を名前で送ると 200（受け付ける）が、`NormalAndDeleted`・`All` （名前と数値 3）・`All`（名前）は、サーバー側で例外のリダイレクト（302）になった（Pleasanter 側の挙動。クライアントの名前の送り方の問題ではない）。名前の受け付けは `Deleted` で確かめた
- `Tenants.Get`・`Extensions.Get`・`OutgoingMails.Send` は、試験の `Administrator`（テナントの管理者）で 403 だった。`Tenants` はサービス管理者などの権限が要ると思われるが、確かめていない（権限の付け方を試験に入れていない）

## 確かめていないこと

- 1.5.9.1 以外のすべての版（1.3.x〜1.5.9.0。版ごとの確認は #69）。`Extention`→`Extension`（1.4.7.0）・`DataChange.Types` の数値（1.4.10.0）・`Since`・`Until` の境界
- `Import`（ファイルの部品の名前 `file`。`Binaries/upload` では確かめたが、`Import` のフォームは試していない）
- `GetLicenseInfo` が 1 日の API 回数の上限（`LimitPerDate`）に数えられるか（上限が既定で無制限のため）
- 改変版・独自ビルドの Pleasanter で `Version` がタグの版と一致するか
- `Tenants`・`Extensions`・`Copy site package`・`MoveSite`・`SynchronizeSummaries`・`GetClosestSiteId`・`ExtendedSql`・`Items.Create` のサイト・Wiki・Issue 形式（結果の表だけで確かめた）、`Depts`・`Groups`・`Users` の `Import`
- `OutgoingMails.Send` の成功（メールサーバーの設定が要る）
- SQL Server・MySQL（クライアントは DB に依存しない見込みだが、確かめていない）
